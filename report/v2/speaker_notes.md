# STOILO v2 — заметки к докладу

## 1. Титульный слайд
Главная рамка доклада: это не просто BOINC-проект, а Python-слой над BOINC для распределённого ML. Логотип с обезьянкой можно использовать как визуальный якорь: STOILO — дружелюбный Python-инструмент поверх тяжёлой распределённой инфраструктуры.

## 2. BOINC даёт добровольные вычисления
Сначала объяснить BOINC простыми словами: есть сервер проекта и много добровольных клиентов. BOINC уже умеет планировать задания, доставлять файлы, запускать клиентское ПО и поддерживать репликацию. Но для ML-инженера этого недостаточно: отсутствует удобный высокоуровневый Python-интерфейс.

## 3. До меня и мой вклад
Смысл слайда — показать, что работа не изобретает BOINC с нуля, но закрывает незакрытую нишу. PyMW и PythonMw показывали направление: Python и BOINC можно связать. Но в них нет цельной современной системы с runtime-сборками, простым деплоем и ML-обёртками. STOILO впервые собирает эти элементы вместе.

## 4. BOINC даёт базу. Я добавил два слоя
Это ключевой слайд про границу вклада. Нижний слой — BOINC, готовая платформа. Средний слой — инфраструктура STOILO: Python-задачи, сервер, runtime, валидация. Верхний слой — ML-обёртки. Если у комиссии возникает вопрос «что именно сделано», возвращаться к этому слайду.

## 5. Python-функция становится BOINC-заданием
Показать путь задачи. Пользователь передаёт Callable и аргументы. Сервер STOILO превращает это в BOINC workunit. Добровольный узел получает подходящую runtime-сборку, выполняет функцию и возвращает результат. Пользователь при этом остаётся в Python-модели.

## 6. Минимальный пользовательский API
Главный акцент — простота. Это не C/C++-приложение под BOINC, а обычный async Python API. За счёт асинхронности задачи можно комбинировать через asyncio и строить более сложные сценарии.

## 7. Репликация и валидация
Добровольная среда недоверенная. BOINC решает часть проблемы репликацией, а STOILO даёт пользователю способ описать, какие ответы допустимы и когда два результата эквивалентны. JSON-результаты уменьшают риск небезопасной десериализации на сервере.

## 8. Среды исполнения Python
Вторая важная трёхуровневая схема. BOINC работает с приложениями, а Python требует интерпретатор и зависимости. Поэтому вводятся: спецификация окружения, вариант runtime и конкретная сборка под платформу. Это сохраняет BOINC-кэширование: одно приложение используется во многих задачах.

## 9. Runtime собирается автоматически
Показать практическую часть. Из JSON-спецификации получается идентификатор flavor. Скрипт сборки берёт нужный Python, создаёт окружение, ставит зависимости и делает бинарь под платформу. Новые runtime можно добавлять без остановки сервера.

## 10. Облачный сервер
Тестирование развёртывания. Система не является централизованным сервисом: её должна развернуть организация, которая привлекает ресурсы. В работе это проверено в Яндекс Облаке: сервер и БД подняты, домен и TLS настроены, клиенты подключаются извне.

## 11. Разнородные узлы
Тестирование гетерогенности. Подключены физические устройства за NAT: Windows x86_64, Linux x86_64, macOS Arm64. Сервер выдавал задачи разным платформам и выбирал подходящие сборки исполнения.

## 12. Синхронное data-parallel обучение
Переход к ML-слою. Поверх STOILO реализована синхронная схема: фиксируется модель, данные делятся на части, узлы считают частичные градиенты, сервер их усредняет, затем вызывается optimizer.step(). Акцент: модель и оптимизатор остаются PyTorch-объектами.

## 13. Стратегию можно менять
Показать, что STOILO не зашивает один алгоритм. В частично синхронной схеме можно ждать только долю результатов и отбрасывать запоздавшие градиенты. Это важно в добровольной среде, где узлы разнородны и нестабильны.

## 14. Обучение модели
Это проверка состоятельности концепции, не соревнование за SOTA. На CIFAR-10 обе схемы устойчиво снижали loss и достигли accuracy 79% и 76%. Значит, ML-обёртки действительно работают поверх BOINC/STOILO.

## 15. Что сделано
Коротко собрать результаты: Python-инфраструктура, runtime-сборки, деплой, разнородные узлы, ML-обёртки, обучение модели. Этот слайд нужен как формальный список результатов.

## 16. Главный вывод
Главная формулировка: BOINC удалось поднять до удобного Python-инструмента. Раньше — C/C++ и ручная интеграция. Теперь — Python и гибкие распределённые сценарии. Подчеркнуть новизну и потенциальную полезность: такой цельной связки раньше не было.
